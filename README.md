# JobSearch AI

Платформа пошуку роботи з AI-помічником (портфоліо-проект).

## Стек

- **Next.js 16** (App Router, TypeScript, Tailwind CSS 4)
- **Drizzle ORM** + **Neon Postgres** (планується)
- **Claude API** — парсинг резюме, чат-помічник
- **Embeddings (OpenAI/Voyage)** — семантичний матчинг вакансія ↔ кандидат

## Запуск

```bash
npm install
npm run dev
```

## Статус

🚧 MVP: auth, CRUD вакансій, заявки, AI-парсинг резюме, семантичний матчинг готові.

## Безпека

⚠️ Проект залежить від Next.js 16.2.11+, яка патчить [CVE-2026-64642](https://github.com/vercel/next.js/security/advisories/GHSA-6gpp-xcg3-4w24) — обхід middleware/proxy-автентифікації в App Router на Turbopack. Тримайте Next.js в актуальному стані.

Кожна приватна сторінка додатково перевіряє сесію й роль на сервері через `requireRole()` (`src/lib/require-role.ts`) — другий рівень захисту, незалежний від `proxy.ts`, на випадок подібних вразливостей middleware в майбутньому.

## Налаштування БД (Neon + Drizzle)

1. Створіть проект на [Neon](https://console.neon.tech), скопіюйте connection string.
2. Скопіюйте `.env.example` у `.env` і вставте `DATABASE_URL`.
3. У Neon SQL Editor (або через міграцію) увімкніть pgvector: `CREATE EXTENSION IF NOT EXISTS vector;`
4. Застосуйте міграцію: `npm run db:migrate` (або `npm run db:push` для швидкого прототипування без файлів міграцій).
5. Переглянути дані: `npm run db:studio`.

## Схема даних

- `users` — акаунт з роллю (candidate / employer / admin)
- `candidate_profiles` — профіль кандидата, `embedding` для семантичного пошуку
- `employer_profiles` — профіль компанії. **`companyName`** (юридична назва, звіряється з ЄДРПОУ при верифікації) окремо від **`displayName`** (публічний бренд, показується кандидатам — наприклад, ФОП працює під впізнаваною франшизою "Kava Milano", а юридично зареєстрований як "ФОП Петренко О.В."). Якщо `displayName` не задано — всюди показується `companyName`
- `jobs` — вакансії, `embedding` опису для матчингу
- `reports` — скарги на вакансії (антифрод)

## Антифрод / модерація

- **AI-модерація вакансій** (`src/lib/moderation.ts`) — при спробі опублікувати вакансію Claude (`claude-haiku-4-5-20251001`) перевіряє title+description на 4 категорії: `mlm`, `scam`, `spam`, **`exploitation_risk`**. Якщо флагується — статус автоматично стає `pending_review` замість `published`, причина й категорія зберігаються в `jobs.moderationReason`/`moderationCategory`, видимі employer'у на дашборді
  - **`exploitation_risk`** — окрема важлива категорія: вакансії, де вимоги до зовнішності/віку/статі не мають професійного обґрунтування для заявленої посади (типовий патерн маскування вербування в секс-індустрію/трудову експлуатацію під нібито звичайну роботу — "прибиральниця, дівчина 18-25, приваблива зовнішність"). AI навчений відрізняти це від легітимних випадків (кастинг акторів/моделей, де вік/типаж дійсно частина ролі)
  - На `/admin/jobs` такі вакансії виділяються червоним і йдуть першими в списку, з довідкою про Національну гарячу лінію з протидії торгівлі людьми (527) та поліцію (102)
- **Scam-патерни розширено**: передоплата/застава, продаж курсу під виглядом вакансії (типова схема: "адміністратор соцмереж" → зовнішній тест → "ви пройшли" → "спочатку платний курс" → мовчання), **платні "інформаційні послуги" кадрових агенцій** (договір на "інформаційне обслуговування" за 500-1500 грн, натомість — список вакансій, які й так у відкритому доступі на OLX тощо), аномальна зарплата для простої надомної роботи (включно з "роздача листівок 500+ грн/день")
- **Bait-and-switch евристика** (`src/lib/bait-heuristic.ts`) — класична схема "Імекс-Дніпро" та подібні: людину заманюють на просту вакансію (листівки/охорона/вантажник/водій/офіс), а на місці кажуть "цю посаду вже зайняли" і пропонують консультанта з оплатою від продажів. Це відбувається офлайн, тому AI не бачить нічого підозрілого в самому тексті — але **1 вакансія для неверифікованих вже блокує класичну версію схеми** (не можна залити пачку приманок з одного щойно зареєстрованого акаунту). Додатково: якщо employer одночасно має 3+ вакансій з "простих"-приманкових назв — на `/admin/jobs` і `/admin/employers` з'являється сигнал для ручної перевірки (НЕ автоблок — легітимні склади/логістичні компанії теж наймають пачками)
- **Пакетування ролей в одному оголошенні** (`src/lib/bundled-roles-check.ts`) — та сама bait-and-switch схема часто йде одним оголошенням: "Потрібні роздавальники листівок, водії, вантажники, охоронці, офісні працівники". На відміну від евристики вище, це видно прямо в тексті **одного** оголошення до публікації — тому тут **жорсткий блок (403)** для всіх employer'ів, не тільки low-trust: легітимних причин пакетувати кілька непов'язаних професій в одному оголошенні практично немає (одна вакансія = одна посада)
  - Причина скарги "На місці запропонували іншу роботу" + попередження в `SafetyTip` — головний захист, оскільки підміна стається виключно офлайн
- **Важливе обмеження AI-модерації**: схема "продаж курсу" зазвичай розгортається *поза платформою* (зовнішній сайт, згодом） — у тексті самої вакансії часто немає нічого підозрілого, і жоден автоматичний аналіз тексту це не впіймає заздалегідь. Тому додано:
  - `SafetyTip` — попередження прямо на сторінці вакансії: легітимний роботодавець не бере оплату за тест/курс перед працевлаштуванням
  - Окрема причина скарги "Направили на платний курс/тест замість найму" — головний *запізнілий* запобіжник: постраждалий кандидат повідомляє, вакансію знімають для інших
- **Trust-gate** (`src/lib/trust-gate.ts`) — жорсткі блоки (не "на розгляд", а прямий `403`) для роботодавців з низьким рівнем довіри (ФОП незалежно від верифікації, або будь-хто неверифікований):
  - Заборона зовнішніх контактів у тексті вакансії (Telegram/Viber тощо), включно з обфускацією ("песик"/"собака" замість "@", розбиття юзернейму)
  - Заборона публікації вакансій моделі/танцівниці/співачки/акторки та подібних ролей без верифікації (легітимний театр/кіностудія/агенція просто повинні спершу верифікуватись)
  - **Заборона публікації вакансій "особистого водія" з ознаками охорони/тілоохоронця** без верифікації — вимоги на кшталт володіння зброєю, силове/екстремальне водіння, досвід силових структур/ЧВК є червоним прапорцем для вербування в кримінальні угруповання під виглядом водія. Звичайна вакансія водія без цих ознак не блокується
- **`/admin/jobs`** — адмін-панель зі списком вакансій на модерації, кнопки "Схвалити"/"Відхилити" (`role: admin`)
- Fail-open: якщо AI-перевірка недоступна — вакансія публікується як є (не блокуємо employer'а через тимчасовий збій AI), про це є лог на сервері
- **Верифікація роботодавців** — `employer_profiles.verificationStatus` (`unverified`/`pending`/`verified`/`rejected`). Employer обирає **тип** (`employer_type`: комерційна юрособа / некомерційна-бюджетна / ЗСУ-МВС-ДСНС / ФОП) і вказує реєстраційний номер (ЄДРПОУ для юросіб, ІПН/РНОКПП для ФОП — лейбл поля міняється залежно від типу) на `/employer/profile` → статус стає `pending` → адмін вручну перевіряє на `/admin/employers` (бачить тип, номер з посиланням на швидкий пошук, домен пошти) і схвалює/відхиляє з коментарем
  - **Ліміт для неверифікованих**: 1 активна вакансія (перевіряється в `POST /api/jobs`) — антиспам-запобіжник, поки адмін не встиг перевірити акаунт
  - **Політика:** без верифікації employer все одно може публікувати (одну вакансію, звичайна AI-модерація все одно діє) — просто без бейджа "Перевірено". Платформа не тільки для юросіб, а й для ФОПів/фізосіб (наприклад, виконроб, що наймає плиточника) — не хочемо відсікати легальний дрібний найм
  - Тип email (корпоративний домен / gmail-ukr.net тощо) — **допоміжний сигнал** для адміна, не автоматичне рішення — ФОП з gmail цілком може бути легальним
  - `isFreeTier` — заготовка під майбутній біллінг: некомерційні/бюджетні організації та сектор безпеки (ЗСУ/МВС/ДСНС) позначаються як безкоштовний тариф автоматично при виборі типу. Самого біллінгу в проекті ще немає — зараз усі публікують безкоштовно незалежно від прапорця
- Телефон компанії (`employer_profiles.phone`) — опційно видимий кандидатам на сторінці вакансії, керується чекбоксом `phoneVisible` в профілі
- **Скарги** — на вакансію (`/jobs/[id]`) АБО на роботодавця загалом (`/companies/[id]`, кнопка "Поскаржитись на роботодавця" — на випадок, якщо employer видалив конкретну вакансію після співбесіди, доказ не губиться). Кожна скарга обов'язково прив'язана до `employerId`; `jobId` — опційний, `ON DELETE SET NULL` (не `CASCADE`) + `jobTitleSnapshot` зберігають контекст навіть якщо вакансію згодом видалили. `/admin/reports` — адмін приймає (пов'язана вакансія автоматично закривається, якщо вона ще існує) або відхиляє
- **`/admin/bans`** — "кандидати на бан": employer'и з 3+ прийнятих скарг АБО 3+ вакансій, які адмін вручну відхилив на `/admin/jobs` (`jobs.rejectedByAdmin`). Список для **ручного** рішення, не автобан. При бані всі активні вакансії employer'а одразу закриваються, публікація нових і редагування блокуються (`403`), employer бачить банер з причиною на дашборді — але акаунт не видаляється й логін не блокується, можна розбанити

### Як отримати admin-акаунт

Реєстрації адміна через UI навмисно немає (не той функціонал, який повинен бути публічним). Зареєструйтесь як звичайний employer/candidate, потім вручну в Neon SQL Editor:

```sql
UPDATE users SET role = 'admin' WHERE email = 'ваш-email@example.com';
```

## AI-парсинг резюме

Кандидат вставляє текст резюме на `/candidate/profile` → кнопка "Розпізнати з AI" викликає `claude-haiku-4-5-20251001` через structured tool use → поля (headline, скіли, досвід, короткий summary) заповнюються автоматично, кандидат перевіряє й зберігає вручну (без сліпого автозбереження).

## Семантичний матчинг (embeddings)

- При збереженні профілю кандидата (`PATCH /api/candidate/profile`) і при створенні/редагуванні вакансії (`POST/PATCH /api/jobs`) генерується embedding (`text-embedding-3-small`, OpenAI, 1536 вимірів) з ключового тексту (headline/скіли/опис)
- На `/candidate/dashboard` — блок "Рекомендовані вакансії", відсортований за косинусною схожістю (`pgvector`, `cosineDistance` з drizzle-orm) між embedding профілю й embedding вакансій
- Генерація embedding не блокує основний запит — якщо OpenAI API впаде, профіль/вакансія все одно збережуться, просто без embedding (спробує оновитись при наступному збереженні)
- **Категорії** (`jobs.category`, `candidate_profiles.preferredCategory`) — 29 категорій: IT, будівництво та ремонт, виробництво, торгівля, водії, логістика та склад, сільське господарство, державні органи, бухгалтерія, освіта, військові, медичні працівники, готельно-ресторанний сектор, **громадське та корпоративне харчування**, **автосервіс/СТО**, **технічне обслуговування**, **пасажирський транспорт**, **залізничний транспорт**, **морський та річковий транспорт**, культура, наука, адміністративно-господарський персонал, шоу-бізнес, медіа, обслуговий персонал, ЖКГ та благоустрій, юридичні працівники, менеджмент та маркетинг, інше.
  - Категорії свідомо розділені там, де змішування шкодить UX: ресторанний шеф-кухар не повинен бачити вакансії їдальні дитсадка в тій самій категорії (професійна образа → миттєвий відхід із сайту, погано для утримання/SEO); зварник в автосервісі не повинен розгрібати вакансії важкого машинобудування, шукаючи "виробництво"; ремонтний персонал заводу (слюсарі, електрики) — це не той самий профіль, що складальники на конвеєрі
  - Embedding-схожість сама по собі не розрізняє сфери (наприклад, "муляр" і "frontend-розробник" можуть здатись схожими просто тому, що обидва — вакансії). Тому коли кандидат вказав бажану категорію, рекомендації жорстко фільтруються по ній (`eq(jobs.category, ...)`) і вже всередині категорії сортуються за embedding-схожістю. Без вказаної категорії — рекомендації йдуть по всіх сферах з попередженням в UI
- **Підкатегорії** (`jobs.subcategory`, `candidate_profiles.preferredSubcategory`) — тільки там, де категорія неоднорідна: `construction` (ІТП ↔ будівельні робітники), `manufacturing` (робітничі професії ↔ інженерно-технічний персонал), `trade` (продавці ↔ адміністратори/менеджери магазину), `drivers` (особистий водій ↔ таксист ↔ кур'єр авто/мото — після виділення `logistics` і `passenger_transport` в категорії "Водії кат. A/B (особисті, таксі, кур'єри)" лишились саме ці три ролі), `medical` (лікарі ↔ середній/молодший медперсонал), `it` (7 підкатегорій: веб/мобільна розробка, десктоп/ігри, low-level/embedded, інфраструктура та сисадмін, AI/дані, кібербезпека, PM/QA). Текстове поле (не enum) з валідацією на рівні API проти `JOB_SUBCATEGORIES` в `lib/job-options.ts` — легко розширити на інші категорії пізніше без міграції типу enum. UI-select підкатегорії з'являється динамічно лише коли для обраної категорії є визначені підкатегорії
- **Для продакшену**, коли рядків стане багато (тисячі+), варто додати `HNSW`/`IVFFlat` індекс на колонки `embedding` для швидкого ANN-пошуку — зараз для MVP-обсягів даних послідовне сканування достатньо швидке
